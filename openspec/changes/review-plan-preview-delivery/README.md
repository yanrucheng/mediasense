# 第6包主方案：保存规划后，页面反映变化

**2026-09-13 已按用户授权进入实现。** 本页保留已定案主方案；当前公开接口已同步至 [Plan Work 合约](../../../docs/spec/contract/plan-work/index.md)。实现、隔离验证及未验范围以 [实施记录](acceptance.md) 为准。下文设计阶段的“本轮不实现/不替换合约”及当时结束位置是历史范围，不是本次开发限制。

任务只有这条循环：**讨论 → Agent保存规划变化 → 工具自动让页面反映变化 → 用户查看并反馈。**

## 一、用户已确认的决定

- 页面从讨论初期就可以存在，不等待完整Candidate。
- 页面内容来自已保存规划及其绑定的PreCheck Result。Agent负责理解、分组、命名和说明；工具负责页面，不让Agent编写HTML、拼图或维护独立展示业务数据。
- 最终仍是看页面、聊天明确接受、冻结对应内容；页面存在不等于已定稿或已确认。
- 采用严格确认：新保存版本，包括工作说明变更，都会使旧版确认失效。刷新、翻页和重新渲染不影响确认；相同请求的幂等重放不另造版本。
- 本轮不进入产品实现、不切换安装、不改业务Plan，不提前替换现行公开合约。也不扩展到其他问题包或清理历史设计。

以下各节是我的设计建议，用具体例子说明如何落实这些决定。

## 二、8项素材只安排了5项

假设本次要整理素材1—8，目前讨论出了两个目录：

| 当前决定 | 保存的规划内容 | 页面显示 |
| --- | --- | --- |
| 素材1、2、3放目录甲 | 目录甲及其3个明确成员 | 目录甲，3项，可展开成员与已有证据 |
| 素材4、5放目录乙 | 目录乙及其2个明确成员 | 目录乙，2项，可展开成员与已有证据 |
| 素材6、7、8还没决定 | 本次范围仍包含它们；暂时没有处置决定 | **待安排3项**，可以查看具体是哪3项 |
| 目前还有疑问 | 保存必要工作说明、已知依据和未决影响 | 在工作说明中显示，明确属于讨论过程 |

页面整体标为：**草案；已安排5/8项；待安排3项；尚未最终确认。**

我的建议是：在同一个Work里保存一份可以继续修改的组织，允许它是部分草案。工具从范围与已保存处置计算剩余项，不把“还没决定”自动改成“保留原位”“排除”或某个兜底目录。

目录名称可以暂定，但主树中的成员范围应已明确。尚无明确成员的目录构想留在工作说明中。页面不猜笔记里的成员，也不另外维护一份展示用组织数据。刚开始只有工作说明、没有目录时，也有可查看的页面。

## 三、补齐、修改、撤回之后

下面的补齐、修改和撤回都发生在冻结前；每次新保存都会让先前的接受不能再用于冻结。已冻结记录保留原样，后续调整另建规划记录（Work），也不继承旧确认。

| 接下来发生什么 | 页面怎样变化 | 旧确认还能否使用 |
| --- | --- | --- |
| 给素材6、7、8补上明确去向 | 已安排8/8项，但仍可标为草案 | 全部有去向不等于用户已经接受 |
| Agent认为已适合整案审阅，提交完整候选 | 显示完整目录、全部处置与重要说明，标为“完整候选，待确认” | 等用户明确接受这一版 |
| 把素材5从目录乙移到目录甲，或者只补一条工作说明 | 保存成新版本，页面反映新的目录或说明 | **旧版确认失效**，需要审阅并接受新版 |
| 撤回完整候选，保留已经确定的部分 | Agent将保留内容保存为草案，页面回到草案状态 | 旧确认不能再用来冻结 |
| 明确清空当前组织 | 页面显示尚无已保存目录，工作说明仍可保留 | 旧确认不能再用 |
| 后来恢复了完全相同的候选 | 页面显示这次重新保存的版本 | 即使内容看起来相同，也不能恢复已经撤回的旧确认 |
| 只是刷新、翻页或修复显示 | 仍是同一份已保存规划 | 不因此重复要求确认 |
| 用户接受当前版，工具核对并冻结 | 显示已冻结及实际确认记录 | 这次接受只对应这个版本；冻结本身不搬动素材 |

当前入口用于继续讨论；最终审阅对应一个确切版本。工具负责记录和核对版本，用户不用记编号或抄摘要。已经打开的旧页不能悄悄混入新内容；发现有新版本时明确提示，再查看新版。

我建议首版明确提示旧页过期，不承诺每一版历史草案都能永久回看或恢复。这不影响保留当前Work及已冻结Plan。

## 四、失败、图片不可读、成员很多时

| 情况 | 用户会看到什么 | 已保存规划怎样处理 |
| --- | --- | --- |
| 规划保存成功，但页面生成或访问失败 | Agent明确说明“规划已保存，当前页面暂不可用”。能打开的旧页标明旧版本；不会冒充最新页 | 保留成功保存的规划，由工具恢复页面，不要求重新讨论或手写HTML |
| 某张预览图片不可读 | 目录、成员和说明仍可看；该图片位置注明素材名称、来源及不可读原因 | 不换一张无关图片冒充，不自动改变该素材归属 |
| 绑定的证据整体无法核对，或成员范围查不清 | 明确说明当前不能完成范围/证据核对，不能据此冻结 | 保留已存规划，恢复核对能力后再继续；不把它当作普通单图缺失 |
| 一个目录有1200项素材 | 显示真实总数，先展示一页，可以实际翻页看文件名与必要来源信息 | 不只给前100个引用，也不把“还有更多”一句话当作展开功能 |
| 翻页时规划已经更新 | 提示方案有新版，引导查看新版 | 不把新版成员追加进旧版列表 |

单张图片缺失不自动让整份方案失效；它是否影响判断，由Agent和用户按实际内容处理。重要限制需要进入相应说明。保存是否成功、页面是否可用、方案是否完整、用户是否已确认，是四件不同的事。

## 五、现有合约为什么需要改变

核实结果很直接：现有工作说明只是自由文本，Candidate必须完整，内部renderer也要求已有完整候选。因此需要把“部分组织”和“持续页面交付”的含义正式补进合约。

| 需要调整的地方 | 为什么 |
| --- | --- |
| **Plan Work的保存内容** | 正式保存上面“已安排5项、还有3项待定”的部分草案；完整候选和可冻结条件仍保持完整要求 |
| **Plan Work的读取与交付结果** | 保存后能取得页面入口，分清当前页和确切版本页；完整显示状态、范围与说明，并诚实报告页面失败 |
| **请求重试的结果含义** | 原保存结果不能重复执行；页面则可能从失败恢复，或已被新版本替代。这两个事实需要分别报告 |
| **最终确认的版本绑定** | 落实已确认的严格规则：工具核对用户审阅版本，不能只因目录摘要没变就沿用旧确认 |
| **Frozen Plan** | 目前无需改变：仍只保存完整最终组织及必要决定说明，不自动带入工作笔记或HTML |

配套Skill会指导Agent从讨论初期建立或恢复Work、保存有意义的规划变化、使用工具入口，以及在接受后冻结对应版本。字段名称和具体实现由我提出，不要求用户选择。上述变化目前都只写在本包草案中，现行公开合约尚未替换。

## 六、建议、未决问题与工程支撑

**我的主要建议**是：一份Work承载当前草案/完整候选；主树呈现成员明确的组织；工具维护可访问入口与版本；显示失败不丢规划；首版不增加永久历史草案恢复。这些是对已确认目标的具体落实方案，供本次整体审阅。

**真正还需要用户决定的产品问题：目前没有新增的必选分歧。** 严格确认已经决定，不再询问。需要审阅的是这份主方案是否准确落实目标；字段名、端口和框架不是用户选择题。
