## Context

**2026-09-11实施决策。** 用户已授权Agent自行收敛基础方案、具体计划和验收并开发。下文保留初始讨论的证据边界；实施前收敛结论与明确预算以本节及[acceptance.md](acceptance.md)为准。

技术决策：metadata保留逐项Work和事务结果，通过线程内、显式producer范围的SQLite连接复用以及有界批量租约续期减少已测协调开销，事务不跨越外部I/O；运行调度在现有资源上限内使用最多4条常驻ExifTool通道。视频改用PyAV 16.x的FFmpeg绑定，同一视频复用一个容器/解码上下文、按真实PTS选择有限材料，显式限制解码线程；不依赖每帧新子进程。PyAV是核心本地解码依赖，不在运行中自动安装或下载。

默认有限视频准备采用至多3个起/中/尾目标，短片也准备中间目标；只有一/两帧或目标落到同一实际帧时去重。`sample_time_seconds`保留请求目标含义，新增可证明的`decoded_time_seconds`，缺失代表实际位置未知；现有字段不回写为另一种历史含义。新decoder/profile身份隔离旧失败Work，源/metadata及其他未变化成果仍复用，旧Result不变。

剖析证据在 `eval/sessions/260911-1841-hk-preprocess-performance/outputs/metadata-256-before.pstats`，原型及后继实测在 `eval/sessions/260911-2128-precheck-throughput-recovery/`。本次代码/测试/隔离wheel与Host构成交付范围，不切换正在使用的全局安装或业务Dataset。

设计依据沿用[Foundation](../../../docs/design/design-260823-1918-mediasense-foundation.md)、[可复用能力架构](../../../docs/design/design-260830-1527-reusable-capability-architecture.md)、[对象/关系/属性模型](../../../docs/design/design-260825-2235-mediasense-information-architecture/design-260825-2235D-precheck-compression-boundary.md)和[当前合约](../../../docs/spec/contract/index.md)。不重新分配三个产品阶段的权威。

### 目的及问题的生成关系

用户最终需要用可接受的本地计算、模型调用和注意力，可靠地完成大型素材集合的组织。PreCheck 的责任是把原始素材转成可追溯、可质疑、可以继续展开的有限证据；Agent 和用户仍判断这些证据是否足以支持具体组织决定。

相关问题从这条价值路径产生：

```text
明确来源范围和准备义务
    → 选择需要取得的证据
    → 提取 / 解码
    → 校验 / 记录 / 复用
    → 交付实际材料、关系及缺口
    → Agent / 用户作判断
```

任何优化都同时影响取得什么、实际代价及后续调查负担。因此需要在来源安全、可恢复、明确资源约束和约定准备义务内改进成本；不将这些成本机械加成一个没有权重含义的分数。

### 已证实与未证实的原因

| 路径 | 实测／源码支持的判断 | 仍不能据此认定 |
| --- | --- | --- |
| EXIF 执行 | 2,133项同18字段，旧批间并发中位1.363 s，新单进程逐批10.787 s；旧串行11.548 s。新实现保留批量与进程复用，但固定单lane损失吞吐 | 每个设备都该开11进程；受资源约束的新版本必须恰好达到1.363 s |

| 视频提取 | 同843个有效帧目标，OpenCV路线31.800 s、逐帧FFmpeg路线50.593 s；后者启动843个进程 | 1.59倍全由启动造成；OpenCV在所有codec/硬件上都更优。两边库、线程与编码器仍不同 |
| 默认有效采样 | 282次请求duration终点，3次晚于最后实际帧PTS；同一素材的有效帧位全部成功 | 285个视频损坏；少量帧必然足够或必然不足；恢复固定20帧就是产品目标 |
| 验收连接 | 旧scale变更28项完成，证明了机制、合成规模和装配，且明确排除了真实素材性能对照；Foundation已有成本/吞吐要求 | 所有前期验收无效。它们的窄范围证据仍成立，运行品质保留需要补自己的门槛 |

更深层的设计风险是：独立的逐项身份/失败责任，被实现或测试习惯带成逐项进程、查询、提交和验证；同时，已终结工作数量容易被当作有效准备结果。前者是本次需要通过剖析验证的结构性假设，不是已量化的全部根因。后者必须通过明确定义成功与验收来避免。

## Goals / Non-Goals

### Goals

- 让有效材料、准备义务、实际成本、约束和缺口共同决定运行品质，保留已有来源安全与恢复保证。
- 固定承诺的含义与权威位置，保留批量、并发、解码器、采样方法和存储原语的替换自由。
- 在用户委托判断的授权下，先收敛基础方案、可读案例和可执行计划，再开发；每步固定输入条件、期望结果、反例、度量与证据出口。
- 让同工作量微基准、默认业务配置、复用/局部变更、安装入口和规模边界各证明自己的命题。

### Non-Goals

- 新的阶段、Tool、质量状态机、策略注册表、全局调度服务或批次持久权威。
- 固定每批200项、一个或11个ExifTool、每视频3/20帧、某种decoder或数据库作为长期契约。
- 缩减当前承诺的摄影字段、来源证明或失败信息；恢复全量高成本视觉处理。
- 无条件承诺所有素材在任意机器上不慢于旧版；把代理素材结果外推到原始长码流。
- 用局部采样自动保证最终语义正确、全场景发现或 Plan 无需进一步调查。

## Proposed decisions

### 1. 以一组有条件的产品承诺约束实现

| 承诺 | 稳定含义 | 权威归属 |
| --- | --- | --- |
| 准备结果 | 对确认范围，尝试并交付约定的metadata/选中视觉证据；缺值、未准备、失败和有效结果分别可读 | 当前 Run 的准备义务；Read 的对象、属性及关系 |
| 效率与资源 | 在明确的资源条件下完成相同有效工作；避免已有效成果的无意义重做；披露实际有效配置与重要限制 | Run执行/配置与已有诊断；量化认证在对应评测配置和发布验收 |
| 安全与恢复 | 来源只读、成功可复用、坏项局部化、控制可落实、旧Result不可变；未知异常不伪装正常等待 | Run/Work/Artifact机制与现有阶段合约 |
| 交付与判断 | 材料真实可读，实际来源/采样位置/压缩范围与局限明确；Agent判断是否足以作具体组织决定 | Read以及既有Plan职责 |
| 发布证明 | 指定工作负载/资源/版本上的质量、时间、复用和故障门槛满足，且安装入口实际接通 | OpenSpec变更计划 → 评测/测试 → 现有迁移台账；不是新的结果实体 |

公共合约固定“什么算满足、什么必须披露、什么不能发生”；配置固定某次有效策略和资源上限；验收配方固定可复核的输入和数字；实现自由选择方法。普通用户不需要选择batch大小或decoder进程数。

性能目标的数字须带工作负载和环境。来源只读等不变量由Tool强制；耗时/质量目标由有界场景认证。进程数等能执行的上限与内存估算/观察值要区分，不能把估算的128MiB申请当成FFmpeg实际内存硬保证。

### 2. 保留逐项语义，允许共享物理工作

Work/Observation对每个明确主体负责，不要求一个主体对应一个新进程、一个事务或重复的一次来源读取。批次或decoder会话可以是短暂执行组织：成功、错误、依赖和失效仍能回到各项。

候选方法包括受资源控制的多个常驻ExifTool、批量准备/认领/提交既有Work、复用已足够的来源证明、按视频共享probe/decoder和多个帧的物理提取。先剖析再选具体原语；不新增“Batch Work”来掩盖逐项结果。

纯批次成员、队列顺序或并发设置变化，在不影响结果含义/有效性的情况下不应使有效材料全部失效；确实影响语义或有效性的变化必须声明依赖。暂停、崩溃和单项坏数据不能使整批已成功结果消失。

### 3. 分开五种成功含义

1. 工作已终结：成功、复用或已终结失败；沿用现有progress计数。
2. 来源已完整对账：已确认范围中每个条目均有解释。
3. 所选准备义务被满足：实际取得的材料符合这次有效策略；不能由前两项推出。
4. Result符合当前Plan入口：沿用已有readiness与导航/异常规则，不等于最终语义充分。
5. 该发布的运行品质已认证：在声明场景中同时满足准备、效率、恢复和交付验收。

它们是现有事实的不同判断，不新增五个运行状态。真实来源缺失与正常有限采样仍可交付带限制的Result；不能通过把实现错误标为“局部失败”就宣布该能力的发布质量达标。本方案也不默认把每个合法局部失败升级成全Run阻塞。

### 4. 以可读案例固定准备与交付含义

以下案例约束准备与交付含义，不创建独立 schema 或固定一种采样算法。

| 案例 | 期望可交付内容 | 不允许的结论 |
| --- | --- | --- |
| 实测稀疏视频：duration=12.3123，实际帧PTS为0、4.1041、8.2082；该例准备目标为起/中/尾的有限材料 | 在有效帧位置完成该目标；各Evidence保留可证明的位置/精度，来源与有限采样说明可读；重复落在同一帧时诚实去重 | 将10或12.3123当作已经取得的帧位置；把空输出当成源损坏；用重复帧凑三个位置 |
| 可解码内容本身只有一帧 | 提供该帧并说明可用材料和时间证据的边界 | 制造多帧覆盖，或仅因不是3/20帧就判坏源 |
| 一个真实坏视频与多个正常视频 | 坏源原因局部保留；其他成功材料可继续使用、复用 | 漏掉坏源、抹掉已成功材料，或重试整个素材集 |
| 2,134项完整metadata profile | 保留当前承诺的摄影字段、缺值、候选/侧车来源和失败；计时区分读取与协调 | 用18字段微基准替换正式profile以获得更快数字 |
| 暂停/重启后只改变一个视频的采样语义 | 未受影响metadata和其他视频材料复用；受影响依赖重新计算；旧Result不变 | 删除全部缓存后把重新跑通称为恢复成功 |

`video_frame.sample_time_seconds` 保留请求目标；`decoded_time_seconds` 仅在 PTS 有证明时存在。basis 记录真实 producer、视频流起点、时间基准与选帧方法。默认按最接近的时间基准 tick 解析目标，再选择该处或之前的帧；没有先前帧时保留首帧。源时间戳和请求的小数舍入差异可由 basis 解释。历史缺失实际位置保持未知，旧 Result 不变。

### 5. 用联合验收防止优化转移成本

同工作量比较控制输入、字段/有效帧目标、输出规格与资源条件，并同时记录实际并发。默认业务比较另外说明为什么选这些材料、交付多少、有什么缺口以及后续调查负担。缓存比较报告实际重复提取次数、读取责任和局部失效，不只报告hit率。

旧版是有效基线，不是所有行为的正确性标签。必要的新保证可有代价，但须显式纳入被确认的预算；不能以“架构更可靠”为理由免除测量。正常坏源不计入实现错误率，算法制造的越界采样也不计成媒体损坏。

## Plan and acceptance framework

具体步骤和数字已在修改产品代码之前固定，见 [acceptance.md](acceptance.md) 与 [tasks.md](tasks.md)。当前证据与复现入口见[修复评测](../../../eval/sessions/260911-2128-precheck-throughput-recovery/report.md)。

| 步骤 | 验收责任 | 证据入口 |
| --- | --- | --- |
| 合约与交换值 | 请求位置/实际 PTS、准备义务、资源和认证边界；权威 schema 与全部发布副本一致 | 当前 Run/Read、合约边界测试、wheel 字节校验 |
| metadata 协调与并发 | 逐项成功/失败和事务边界不丢失；线程隔离、批量续租、受控 ExifTool 通道 | 256 项前后 profile、租约/取消/坏项/并发/重启测试 |
| metadata 全路径成本 | 18 字段同值比较；完整 profile 首次/复用满足冻结预算，复用零提取 | 三轮同资源内核、2,134 项两组首次/复用与逐对象比较 |
| 视频正确性与效率 | 默认有限起/中/尾、真实 PTS 与去重；相同有效帧工作量，来源失败与实现失败分开 | 一/两帧、稀疏/VFR/源变动/取消测试；843 帧内容、位置和计时 |
| 交付与恢复 | 联系表引用实际帧；旧 Result 不变，变化只影响真实依赖 | Result/Read、局部变化、全复用与实际安装 Host |
| 发布证据 | 默认测试、源码/wheel 一致性、只读素材完整性；结论不超出实测范围 | 评测 metrics、测试记录、迁移台账 |

ExifTool 每条通道拥有独立进程和顺序协议；可用队列分配通道，只观察一次版本并在阶段结束关闭全部通道。SQLite scope 只复用线程内连接，不包含跨 provider I/O 的事务；长批心跳保留独立线程/连接。

PyAV 为核心本地依赖，运行时不下载；probe 仍用 ffprobe。每个视频复用一个容器/解码上下文，邻近目标顺序解码，远目标后向寻关键帧；在缩小后分配 RGB 并尊重显示旋转。codec 线程数可执行约束；每视频默认 20,000 次解码帧/120 秒为协作式检查，单次底层调用返回后才能观察取消/时限。内存按源尺寸估算用于准入，不宣称是 RSS 硬上限。缺解码依赖明确 blocked 并允许修复后 resume；冻结资源上限不足时说明需取消并以适当配置开启后继 Run，不声称 resume 会自动改写旧配置。

## Risks / Trade-offs

- 增加并发可能转移为内存/磁盘压力 → 先固定可执行的资源包络，记录实际峰值与适用范围；不把旧11进程当所有机器默认。
- 批处理可能扩大失败/恢复范围 → 逐项提交和失败责任保留，验证中断与一坏项旁的成功项。
- 新的强准备义务可能被误读为全语义覆盖 → 只认证有限准备目标与真实交付；语义充分性由Agent/用户判断。
- 厂商metadata语义在其他变更中演进 → 本计划锁定有效profile；语义改变重新确认相关数据与失效门槛，不合并独立维护体系。
- 代理素材掩盖长码流问题 → 日常回归保留当前配方；原始长视频/物理盘认证仅在决策确实依赖它时扩展，单独声明范围。
- 硬性时限可能诱使省略内容或吞错 → 质量/覆盖/失败先为共同前提，首次与复用一起验收；预算达不到则报告未达标。

## Migration Plan

当前公开 Run/Read 已先行补齐上述含义；JSON schema 的合同副本与 Skill 引用副本同步。Work/Result 的私有数据库 schema 不变，新信息沿既有 JSON 属性模型承载。

视频 producer 身份变为 `builtin-pts-video-frame-v2`，依赖真实 decoder/library 身份及选帧/编码语义；仅调度线程数不进入帧的语义身份。旧的错误终点 Work 不被当作修复后的结果复用；原 metadata、probe 与其他有效 Work 仍按真实依赖复用。新材料封存到后继 Result，不回写历史字节。

本次交付范围是源码、测试和隔离 wheel/真实 Host 验证；候选包保持当前开发版本并以 SHA-256 标识。没有切换全局安装或业务 Dataset。公开安装升级及更大范围的认证应引用此处证据并完成其自身适用验收。

## Remaining scope and reopening conditions

- 本地代理 fixture 与三个原样短片不足以认证原始长 GOP/长码流、完整 RAW、外置盘、远程存储或其他机器。用户目标依赖这些范围时，增加独立配方和资源证据。
- 有效的有限帧不等于全部场景发现或 Plan 语义充分。扩大视觉调查由后续判断目的决定，不用固定帧数代替判断。
- 厂商规则或正式 metadata profile 语义发生改变、decoder/profile 被替换、实际资源显著超出估算，或新的素材错误影响准备义务时，重开对应依赖与验收；不因当前本机速度通过而豁免后续验证。
