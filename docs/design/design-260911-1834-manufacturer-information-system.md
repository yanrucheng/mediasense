# 厂商信息维护体系：能力边界与演进设计

## 目的与审阅边界

用户已确认名称为**厂商信息维护体系**，并将它定位为 MediaSense 的核心能力。它要持续满足两项目的：按设备和媒体的实际差异提供定制适配；让用户通过简单配置扩充已支持的适配行为。

2026-09-12，用户确认目的与内在逻辑，选择 B 方案（随包基础知识＋用户按厂商维护的增量目录），并授权先固定文件契约再开发。本页维护设计理由；文件字段和生效行为由[当前厂商知识契约](../spec/contract/manufacturer-knowledge/index.md)定义。迁移与实际验证仍在[既有迁移台账](../eval/eval-260823-1918-ai-album-migration-baseline/eval-260823-1918B-capability-ledger.md#manufacturer-information-delivery)维护，不将实现检查冒充发布或所有设备认证。

体系的稳定责任是：**持续维护当前媒体业务所需、无法仅凭用户素材及附带信息可靠确定的厂商行为知识，让它实际参与处理，并允许用户方便地补充和修正。** 第一轮从 AI Album 的时间缺陷、字段来源和选择知识取材。素材自身可读出的型号、序列号或曝光值属于素材观察，不另行登记为厂商事实；通用解析器已可靠解决的部分无需重复维护。

## 非目标

- 不承诺配置能创造任意新算法、解码器或私有格式解析能力。
- 不把所有设备差异简化成品牌名称，也不规定每个品牌必须有一个 Python adapter。
- 不将设备知识与地图、模型等外部服务的 provider 选择合并成通用插件平台。
- 不在本次设计中创建新产品阶段、公共 Tool、Skill、独立服务或最终 stage schema。

## Backward Compatibility Policy

| 项目 | 约束 |
| --- | --- |
| 当前形态 | 在已有 0.10.0 产品上开发文件契约与生产接通；在用环境及候选安装分别认证 |
| 兼容政策 | 沿用[当前合约](../spec/contract/index.md)的零公开 API 兼容政策，不设置长期新旧路由、双写或旧配置 runtime adapter |
| 历史保护 | 已封存 Result 和原始媒体字节不改写；规则修订产生后继结果 |
| 迁移责任 | 实现方逐条审查旧规则的目的和证据，再表达为新规则；用户已有定制需作为显式迁移输入，不能默默忽略 |
| 激活条件 | 用户已授权定稿文件契约并开发；当前契约承接字段、示例及失败语义，安装和发布完成度单独记录 |

旧 YAML 的文件格式不必照搬，但其中有效的可配置能力需要恢复。历史缓存和 AI Album 仓库不成为运行时依赖。

## 系统位置与权威

维护能否真正改善结果，取决于以下关系是否闭合；这也是设计的分解依据：

```text
设备/容器的可核对行为 + 原始媒体观察
    -> 有作用范围的规则与显式用户修正
    -> 本次生效配置及版本
    -> 确定性提取、匹配、解释
    -> 带依据和限制的 Observation
    -> GPX/关联/压缩等消费者
规则修订或撤回 -> 重新判断受影响范围 -> 复用或重算 -> 后继 Result
```

| 信息或责任 | 权威位置与维护者 | 对外边界 |
| --- | --- | --- |
| 原始媒体及其中的字段 | 原媒体；工具只读观察 | 规则不改写原值；来源不同分别保留 |
| MediaSense 随包规则 | `src/mediasense/_resources/manufacturers/` 中的 YAML；由项目维护者维护并随包发布 | 通用字段解析仍归提取器，条件化厂商知识由此维护；安装副本是发布快照 |
| 用户知识与时区上下文 | `<用户配置根>/manufacturers/` 保存知识增量；用户/Dataset `config.toml` 保存 metadata 时区上下文 | Dataset 不再发现第二份厂商知识目录；一次拍摄设置不成为全体同品牌设备的事实 |
| 本次实际采用的规则 | 扩展现有 `MetadataProfile`，由 Host 解析并绑定到 Run | 可查采用了什么、从哪里来、覆盖了什么；恢复不静默读取新规则 |
| 提取及规则执行 | 现有 metadata producer，复杂方法由其内部可替换实现承担 | 不拥有 Plan 的语义判断或 Apply 的执行意图 |
| 结果与重算 | 现有 Work、Observation、Result 和依赖机制 | 规则来源属于 provenance/basis；不新增平行结果实体 |

规则资源有独立维护必要：设备知识应能在不改提取器算法时更新，也应能核对一次输出采用的知识。`MetadataProfile`、配置入口和 Work 已能承担生效选择与生命周期，无需再加一个全局 Registry 服务。首个真实消费者是 PreCheck；跨阶段复用成熟前保持内部能力边界。

## 规则描述什么

厂商是检索和组织知识的入口。适用性来自足以区分正确与错误处理的条件，例如型号系列、固件范围、媒体类型、容器、字段组合以及原片/侧车/转封装来源。只要求对该规则有意义的条件；不知道条件时不能当成已匹配。

每条可维护规则要能回答：适用于什么输入，改变哪项解释，凭什么改变，何时不适用，以及如何验证。必要内容包括规则身份、匹配条件、目标字段或行为、来源证据与适用限制。当前 YAML 字段、add/replace/disable、优先级及同属性冲突由文件契约和其唯一 JSON Schema 定义，本页不复制第二份字段表。

普通配置扩展应支持新增设备别名或匹配条件、已支持字段的来源优先级、时间语义、已实现类型/单位转换，以及明确停用或替换某条规则。新增属性沿现有 Observation 扩展规则声明名称、单位、主体和状态，不能通过改映射让既有属性换义。

需要解析新的私有二进制结构、增加新的转换算法时，由代码实现相应处理能力，再供规则引用。配置使用尚未实现的行为必须被明确拒绝，不能把读取配置成功当作能力执行成功。

## 时间必须保留三个不同问题

| 问题 | 示例 | 依据 |
| --- | --- | --- |
| 字段编码的时间含义是什么？ | UTC 整数容器时钟、本地墙上时间、带偏移拍摄时间 | 格式语义及适用的设备/制作工具规则 |
| 无偏移的设备时钟采用什么时区，是否有校时修正？ | 这台相机在这次旅行期间设为东京时间，或快了 90 秒 | 明确的设备/时间范围设置、可靠来源或用户修正；未知时保留假设 |
| 结果以什么时区表示？ | 统一以 Asia/Shanghai 表示同一时刻 | 输出表示策略，不能反向决定原时钟含义 |

UTC `09:33` 转到东八区是 `17:33+08:00`；本地墙上时间 `17:33` 在已知东八区设置下也是 `17:33+08:00`。两者过程不同，不能由“DJI”一个品牌判断。显式偏移通常提供更强依据；若它本身受已证实的设备缺陷影响，也只能按窄范围规则修正并保留原值。

本轮将 `assumed_timezone` 与 `output_timezone` 分开配置，规则另以 `naive_time` 表达字段语义、以 `shift_seconds` 表达有依据的时钟补偿。历史单一 `timezone` 无法区分这些责任。跨时区旅行、夏令时重复/不存在时刻、相机未校时、制作软件重写时间，都需要保留足以区分它们的依据。缺乏依据时不制造精确拍摄时刻。

## 配置维护如何成为真实能力

普通用户应能沿现有配置入口完成一个有限改动：增加或修正条件与字段规则，查看受影响样本及有效配置，然后在正常安装的 PreCheck 中获得带新依据的结果。不要求编辑包内源码或调用 Python 内部构造器。

随包规则构成基线，用户目录以规则 ID 明确增加、完整替换或停用；不复制整份默认库。最终生效知识形成一份包含原始定义及覆盖来源的快照，保存到现有 Run execution_config。metadata Work 使用该快照身份，Result 的实际观察保留采用依据。doctor 和 Dataset Open 报告配置情况；读取配置成功仍不代表已有规则命中素材。

领域条件和配置来源具有不同含义：用户可以明确覆盖随包默认值，但不同规则对同一字段的竞争不能只靠列表顺序、品牌字符串长短或“最后加载”解决。有明确选择依据时保留所选值及冲突；同等权威的矛盾规则无可靠选择时，返回该属性失败和候选依据，其他独立属性继续处理。合法规则无匹配与配置错误必须区分。

维护者或 Agent 可以用更好的检索、原片调查、统计或推理方法提出规则。激活前的可核对产物是有范围的规则修改和正反例；具体调查步骤不成为永久流程。普通用户修改只影响其显式选择的范围，随包知识的变更仍由项目维护者发布。

首轮用现有 doctor / Dataset Open 检查有效配置；对明确选定的有限样本运行 PreCheck，再经 Read 查看规则命中、未采用原因及观察变化。运行前的配置诊断与实际执行证据分别交付，复用已有入口，不新增预览 Tool。

## 执行、失败与更新

- **提取范围完整。** 规则需要的识别字段与目标字段必须进入实际 ExifTool 请求。字段没采集与采集后缺失分别交代，不能把前者当作规则未匹配。
- **来源保留。** 归一值保留原字段、来源 Source Item、解释方法、生效规则修订、用户修正来源及冲突。复用现有 Observation 的 provenance/basis/qualifications；规则只能解释实际来源，不能推广到被代表的全部成员。
- **执行快照稳定。** Run 固定本次有效规则；配置变更后，恢复旧快照或显式开始后继 Run，不能在半次执行中混合规则。损坏配置、未知行为和不可恢复的执行异常不伪装成正常排队或无字段。
- **失效覆盖潜在影响。** Work 身份覆盖实际规则语义、匹配依据和处理实现。新增规则也可能影响此前未命中的文件，仅记录旧赢家的 ID 不足以保证复用正确。可以先保守重评 metadata，再优化不受影响部分；不得提前宣称已实现精细失效。
- **重算沿真实依赖传播。** 时间变化可改变 GPX 匹配及关联/压缩边界，受影响范围可能包含其他成员。可证明不受影响的图像、embedding 等继续复用。重算不自动授权新的 Geo 外部请求。
- **撤回与封存分开。** 恢复先前规则后可生成新的 Result；已有 Result 和依赖它的冻结 Plan 不被后台修改或自动换绑。没有有效特定规则时，可按已声明通用策略产生有限观察，不因未知品牌整体停摆，也不宣称完成厂商适配。

## 供人工审阅的行为示例

下列输入是合成的区分案例；它们验证规则语义和能力边界，不认证对应厂商的所有设备。

| 输入或改动 | 应具备的行为 | 要排除的错误 |
| --- | --- | --- |
| 已知 UTC 容器字段 `QuickTime:CreateDate=09:33`，显示东八区 | 保留原值与 UTC 解释，得到 `17:33+08:00` | 见视频或品牌就统一加八小时 |
| 本地 EXIF `17:33`，本次设备时区明确为东八区 | 同一显示时间，依据是本地时钟设置 | 和 UTC 容器共用一个未说明的修正 |
| Sony 来源的拍摄值带 `+09:00` | 按有效偏移换算并保留字段来源 | 品牌默认覆盖明确偏移 |
| 某已证实规则范围内，XMP 为 `09:33`、EXIF 为 `17:33` | 规则可选择 EXIF，并保留 XMP 和拒绝依据 | 全局 XMP 优先级消灭厂商例外；反过来抹掉合法侧车修正 |
| 用户新增 ACME 匹配和一个已支持类型的提取字段 | 只改配置即可从安装入口采集、执行并通过 Read 交付 | 仅内存配置或 schema 接受，生产不执行 |
| 只有转封装 Encoder，无可信设备身份 | 保留 Encoder 来源，设备身份仍未知 | 将 Lavf 等制作软件当作相机型号 |
| 两条规则同范围冲突；某规则指定了不存在的处理方法 | 分别交代解释冲突与配置错误，局部观察保持诚实 | 悄悄取首条、忽略错误然后宣称完成 |
| 新规则覆盖此前无规则的文件；撤回后重跑 | 正确重评匹配，更新依赖结果，能复用不受影响工作，旧 Result 不变 | 只看曾命中的规则而继续使用失效缓存 |

## 完成标准与后续顺序

本轮按已讨论的示例和运行/失败语义固定文件契约，再实现并从隔离安装入口验收；逐项结果见迁移台账。不能以 YAML/TOML 文件出现、一个 parser 通过或通用单字段时间测试替代下面的证明。

| 用户目的 | 必须闭合的验收路径 |
| --- | --- |
| 厂商定制适配 | 同品牌不同适用范围及冲突字段 → 正确规则/通用回退 → 保留来源与限制的实际观察 |
| 简单配置扩展 | 干净安装 + 用户 YAML 新增规则与用户/Dataset metadata 上下文 → 提取标签 → Host/Run 执行 → Result/Read 交付；不改 Python |
| 可维护与可回退 | 配置来源可解释、错误可定位、规则修订/新增/停用正确失效、恢复不混版本、旧 Result 字节不变 |
| 运行品质 | 本地、源只读；相关重算与无关复用；正常路径不增加模型或网络成本；大批量匹配成本可测 |

第一轮优先恢复配置表达、实际装配和上述验证，再逐条认证 Sony/Canon/DJI 等已发现的知识。真实设备的格式、固件、侧车或转封装差异需要原片或可信技术材料佐证；代理媒体与合成案例不能填补这一证据。未覆盖的设备只声明未认证，不阻止已验证规则交付。

只有实际需要表明内部规则资源与现有 Profile 无法承担独立调用、维护或生命周期，才重开公共 Tool、Skill 或服务边界。新增厂商、换提取库、换存储格式，以及更强 Agent 的调查方法，不应要求重建该体系。
