# Plan Frozen 产物契约澄清

## 当前设计

本记录已经撤回上一版极小 JSON Mock 和基于它提出的 13 个问题。原因不是字段写得不好，而是它们过早假设了逐项处置、Organization Unit、Placement、Target Root、decision basis 和多层 seal 等结构；这些结构的业务必要性尚未证明。

当前只保留已经确认的阶段边界：

```text
精确 PreCheck Result
→ Plan Working State（可变）
→ Frozen Organization Plan（不可变）
→ 独立 Apply 授权
→ Apply Runtime
```

第 1 轮已确认 Frozen Plan 的业务价值不是建立逐文件账本，而是：继续利用 PreCheck 的压缩结果，在真正改动文件前发现并修正语义错误；对于不可逆或高损失变更，再把已经确认的压缩组织结果固定下来，供 Apply 安全执行。

用户默认审阅组、代表证据、名称和异常，必要时才展开具体 Source Item。百万级范围可以通过精确 Result、已有覆盖关系、紧凑决定和例外恢复出完整成员，不要求复制百万项。Plan 可以对 Result 内成员固定、可机械展开的集合做共同决定，也允许只冻结一个可验证的子范围。

用户确认的是紧凑决定及其在精确 Result 中覆盖的完整成员，不只是屏幕上的 representative。不可逆执行要求 Frozen Plan 固定精确 Result、可机械恢复的受影响集合、确定的最终组织结果和全部例外。

Frozen Plan 保存最终组织分组、最终命名和逻辑存放结构，但不决定 copy、move、hard link、symlink 等 Apply 动作。只有组织结果已经冻结，危险 Apply 才能获得独立授权；预览不受此限制。Apply 负责选择和安全执行具体动作、短期 rewind、实际变化记录、执行效率和完整性验证。

Plan 可以在 PreCheck 压缩集合上做确定组合和少量例外，但不应把大规模修补上游分组当成常态。若 representative 隐藏的差异需要大量拆分，原则上应让 PreCheck 产生更合适的新 Result；Planning Agent 如何调查和判断仍保持开放。Frozen Plan 最终不得保留互相矛盾的决定。

能够支持危险 Apply 的 Frozen Plan 必须让范围内每个源媒体都有明确归属，但不预设这个归属必须通过统一的“组”实体表达。“留在原地”也是完整归属；明确排除 `.DS_Store` 等辅助项或彻底损坏项也可以成立，但必须显示其核算结果和具体理由，不能与遗漏混淆。

Frozen Plan 对正常组织结果只保留最终决定；对异常、容易误解或经过用户特别确认的决定，保留最短原因和必要 Evidence 引用。最终用户确认绑定整份候选内容的唯一不可变身份，任何语义变化产生另一份 Frozen Plan。Plan 固定逻辑根名称和根内完整相对结构，Apply 授权再选择并验证实际父目录或存储卷。

## 证据

- 用户明确指出：AI Album 已经历多轮、多 TB 级实际业务检验，不能因为它没有显式保存某种记录，就直接判定业务功能缺失并引入复杂设计。
- [AI Album migration baseline](../eval/eval-260823-1918-ai-album-migration-baseline/) 记录了旧系统的实际优势：大幅压缩远程模型输入、批量 metadata、可复用缓存、逻辑分组、视频采样与代表选择，并且分析前无需复制完整来源集合。
- 同一 baseline 观察到地点语义传播、机械命名、时间失败伪装成日期和完成质量说明不足；这些事实支持改进 Plan 的理解与审阅，但尚不能证明逐项 Frozen Set、Organization Unit、Placement 或完整审计链是必要产物。
- [MediaSense Foundation](../design/design-260823-1918-mediasense-foundation.md) 已确定 Plan 与 Apply 分阶段，Apply 不增加新的组织语义；本问卷不重新询问该阶段边界，而是澄清这项边界需要多重的持久化交付。
- [PreCheck Read Contract](../spec/spec-260826-1546-precheck-read/) 已提供精确 `result_ref`、压缩入口、展开和追溯能力；Frozen Plan 不需要复制 PreCheck Evidence。

## 已确认决策

1. Plan Working State 与 Frozen Plan 是不同生命周期；Frozen Plan 不应被建模成 working object 的普通状态值。
2. Frozen Plan 绑定一份精确、不可变的 PreCheck Result；Dataset 信息从 Result 取得，不另建第二权威绑定。
3. Frozen Plan 不等于 Apply 授权；真实文件系统变更在 freeze 后独立授权。
4. Apply 不得补充事件识别、命名、分组、目标选择或异常取舍等新的组织语义。
5. PreCheck Evidence 只被精确引用，不复制进 Plan。
6. 私有推理链、完整对话、VLM payload、查询流水、临时候选、Apply journal 和 receipt 不属于 Frozen Plan。
7. “AI Album 没有显式保存 X”本身不是引入 X 的充分业务理由。
8. 上一版问卷提出的逐项 disposition、Organization Unit、Placement、Target Root、decision basis、confirmation/seal 分层全部重新开放，不再视为默认结构。
9. Frozen Plan 的首要业务价值是让用户在真实文件变更前，以压缩形式审阅、修正并确认最终组织结果，而不是逐文件做账。
10. 只有移动、重命名、删除或改变唯一来源位置等不可逆或高损失变更，才强制要求 Frozen Plan；预览和可重建输出可以采用更轻的流程。
11. 用户默认审阅组织分组、代表证据、名称和异常；需要时再展开具体 Source Item，不要求逐项查看百万项。
12. Frozen Plan 至少保留到 Apply 完成并验证。执行完成后的长期归档、比较、重放或 rewind 尚未被默认承诺。
13. 百万级闭合允许紧凑表达：精确绑定 Result，复用 Result 中可机械展开的覆盖关系，并记录 Plan 决定与例外；不要求把所有 Source Item 复制进 Frozen Plan。
14. Plan 可以对精确 Result 内成员固定、可机械展开的一组 Source Items 作共同决定；PreCheck 关系只提供成员边界，组织决定仍属于 Plan。
15. Frozen Plan 可以只处理 Result 的一个明确子范围；该范围必须可机械验证，范围外内容不能靠含糊省略表达。
16. 用户确认紧凑决定时，同时确认它通过精确 Result 覆盖的全部成员；不要求逐项点击，但界面应能展示数量、代表、异常和展开入口。
17. Planning Agent 如何判断继续展开还是 Reopen 属于开放方法。稳定契约只要求：Frozen Plan 绑定精确 Result；若最终改为绑定新 Result，则产生新的 Frozen Plan，不原地改写旧 Plan。
18. 不可逆执行的最小安全交接包括：精确 Result、可机械恢复的受影响集合、确定的最终组织结果和全部例外；不要求复制逐项清单或完整推理过程。
19. 除执行中故障恢复外，用户希望在 Apply 刚完成后的短安全窗口内仍可反悔并恢复执行前布局；不要求永久撤销任意历史执行。
20. Plan 原则上基于 PreCheck 已有压缩集合进行组合；可以使用确定集合运算和少量明确例外。若现有 representative 隐藏需要大规模拆分的重要差异，通常应由 PreCheck 产生更好的新 Result，而不是让 Frozen Plan 维护大量补丁；具体调查方法仍保持开放。
21. Frozen Plan 不允许留下互相矛盾的覆盖决定。若同一 Source Item 确实应有多个组织结果，必须由 Plan 明确表达这些结果，不能由 Apply 选择。
22. “这些媒体属于同一组”、最终组名以及最终逻辑存放结构属于 Plan 的组织决定，应保留在 Frozen Plan；它们不等同于实际文件操作。
23. Frozen Plan 不决定 copy、move、hard link 或 symlink，也不负责选择执行优化。它只证明组织结果已经完成并冻结；危险 Apply 只能在此基础上另行授权。
24. Apply 负责安全、实际执行记录、短安全窗口内的 rewind、机械执行效率和执行后信息完整性；这些责任不得反向进入 Frozen Plan。
25. Frozen Plan 可以通过确定集合运算和少量明确例外修正 PreCheck 集合，但大规模拆分原则上应促成新的 PreCheck Result，而不是让 Plan 维护大量补丁；这是一项产物质量倾向，不是固定 Planning Agent 流程。
26. Frozen Plan 不允许互相矛盾的覆盖决定。若同一 Source Item 确实参与多个不冲突的组织结果，Plan 必须把这些结果明确为一个确定整体，Apply 不作取舍。
27. 用户确认的最终分组、组名、文件夹名和逻辑层级属于 Frozen Plan。Apply 只负责把这份逻辑组织结果以获授权的具体动作落地。
28. 对于能够支持移动、重命名、删除等危险 Apply 的 Frozen Plan，每个范围内源媒体必须有明确归属；“保留在原地”属于明确归属，不等于未处理。
29. 辅助项、彻底损坏项或其他确实不进入组织结果的例外可以被排除，但必须被明确核算并记录具体理由；不能用沉默省略表达。
30. 不要求所有归属都通过一个统一的 `Organization Unit` 实体表达。正式契约只需确保每个范围内源媒体的最终逻辑归属可确定，并保存确有业务意义的分组、组名和目录层级。
31. 正常组织结果只需保留最终决定；异常、容易误解或用户特别确认的决定保留最短原因和必要 Evidence 引用，不保存完整推理过程。
32. 一次最终用户确认绑定整份候选内容的唯一不可变身份；任何会改变组织语义的内容变化都产生另一份 Frozen Plan。
33. Frozen Plan 固定逻辑根名称以及根内完整相对结构；Apply Authorization 选择并验证当前实际父目录或存储卷，绝对挂载路径不成为 Plan 的组织权威。

## 问题清单

### 第 1 轮：Frozen Plan 的业务前提

本轮只问 5 个上游问题，分为“为什么需要”和“需要到什么程度”。这些问题不预设逐项清单、组织实体或目标模型。请在“你的回答”后写选项字母，也可以直接用自己的话改写。

#### Q1. Frozen Plan 相比 AI Album 的直接处理流程，最重要的新价值是什么？

为什么问：如果说不清它给用户增加了什么实际能力，就没有理由为它设计复杂产物。

简单例子：AI Album 可以直接生成整理后的目录。MediaSense 可以先把建议结果给用户看，用户改完再执行。这里新增的价值可能只是“执行前能看和能改”，不一定是保存百万项审计记录。

选项：

- A. 让用户在真正改动文件前，看到并确认最终组织结果；这是首要价值。
- B. 让 Plan 和 Apply 可以由不同进程或实现独立完成；交接本身是首要价值。
- C. 长期保存每次计划，便于以后重放、比较和审计；历史追踪是首要价值。
- D. AI Album 的直接流程已经够用；目前没有证明需要独立 Frozen Plan。
- E. 多项同等重要，请写明具体优先级和真实使用场景。

推荐：A。原因：现有证据最直接支持“语义结果需要被用户纠正”，而没有证明用户需要逐项审计或长期重放。若实际首要价值是其他选项，后续契约形状会明显不同。

你的回答：A. 事实上，真实的业务场景是，如果用户发现之前做的一个绑定，就比如说前面有2000个照片全部被判定为一组，然后只有一个representative。在plan阶段就发现这个不一样的话，用户在plan阶段就会把这搞定。所以等到了apply阶段，就是产物这一段，仍然是应该有一个这样子的压缩的概念在。就是如果真出错了，不是靠逐文件的一个绑定计划，而是靠把压缩做好，也许是返工，也许是什么，可以在plan阶段发现。也就相当于把这个问题抛回了precheck阶段，能理解我意思吗？不过在查看问题二的时候，我意识到了，就是刚上面描述的更多是一个from now阶段的一个，就是即使最后百分百确定了，我们在做出不可逆的时候也仍然还是需要一个foren set，但它的目的就不一样了，它的目的是保证一个安全性，如果用户反悔的话，我们至少还应根据这个留有一定的信息，也许还可以做一个rewind

#### Q2. 哪类实际文件变更值得要求先形成 Frozen Plan？

为什么问：只生成预览图与移动原始文件的风险完全不同。若所有操作都要求同样重量的计划，可能给低风险流程增加没有收益的负担。

简单例子：生成一套可删除的缩略图目录，做错了可以重跑；移动唯一一份原始照片，做错了可能很难恢复。

选项：

- A. 只要会生成任何输出，都必须先有同样完整的 Frozen Plan。
- B. 只有会移动、重命名、删除或改变唯一来源位置的高风险操作必须冻结；预览和可重建输出可以更轻。
- C. copy、link 和 move 都必须冻结，但纯预览不需要。
- D. 不按操作类型区分；只要用户明确要求执行，就直接运行。
- E. 需要按其他风险边界区分，请说明。

推荐：B。原因：它把设计成本放在不可逆或高损失场景，最符合“没有业务损失就不增加实体”的原则。低风险输出是否仍复用同一种紧凑计划，可在后续决定。

你的回答：B. 我其实觉得你说的对，就是这种不可返回的，至少它应该生成一个FrozenSet，好像是有道理的。不然就完全失去了回溯的一个能力了。有道理

#### Q3. 用户实际需要审阅到什么粒度？

为什么问：用户是否真的要看百万个条目，决定了 Frozen Plan 是紧凑的组织提案，还是逐项审计账本。

简单例子：十万张旅行照片被分成 80 个活动。用户可能只想看 80 个组、代表图和异常项，只有怀疑某组时才展开成员，而不是逐项确认十万行。

选项：

- A. 默认审阅组织单元、代表证据、名称和异常；需要时再展开到具体 Source Item。
- B. 冻结前必须逐项查看或确认每个 Source Item。
- C. 只看最终目录树，不需要代表证据、异常或展开能力。
- D. 不设统一粒度，由 Agent 自行判断何时给用户看什么。

推荐：A。原因：它保留 PreCheck 压缩带来的成本优势，也符合 AI Album 已验证的大规模工作方式；同时允许用户挑战高影响区域。

你的回答：A

#### Q4. Frozen Plan 在首次执行完成后，还必须承担什么用途？

为什么问：如果产物只用于紧接着的一次 Apply，就不应为了长期历史用途加入版本谱系、完整依据和大量审计信息。

简单例子：用户确认一次香港照片整理并立即执行。半年后，他是否需要重新打开当时的 Plan、比较新版，或者在另一块磁盘上重放同样结果？

选项：

- A. 只需可靠支撑一次 Apply；执行和验证结束后，无长期产品用途。
- B. 至少在 Apply 完成并验证前保留；完成后是否归档由产品策略决定。
- C. 必须长期支持查看、比较和解释历次 Plan，但不承诺直接重放。
- D. 必须长期支持在兼容来源上重放同一 Plan。
- E. 不同数据集或操作风险需要不同保留级别，请说明。

推荐：B。原因：它满足阶段解耦和失败重试的直接需要，却不凭空制造长期审计与重放产品。若真实业务确实需要 C 或 D，再为其增加必要信息。

你的回答：B

#### Q5. 在百万级 Source Items 下，怎样才算“没有漏项”并且值得用户信任？

为什么问：这是决定是否需要逐项 Frozen Set 的根问题。业务上需要的是可信结果，不一定是百万行重复名单。

简单例子：PreCheck Result 已核算 100 万项。Plan 说“这 999,980 项按已确认的 80 个组处理，20 个异常逐项列出”，并能机械验证无重叠、无遗漏。另一种方案是把 100 万项全部复制进 Plan。

选项：

- A. Frozen Plan 必须显式列出每个 Source Item 及其决定，否则不算可信。
- B. 可以用精确 Result 引用、确定的组或规则、例外清单和可验证的无遗漏证明紧凑表达；不要求重复百万项。
- C. 只要最终目录看起来合理即可，不需要证明覆盖或解释异常。
- D. 由 Apply 运行时自行发现未覆盖项并决定如何处理。

推荐：B。原因：它保留业务上的可验证性，同时不牺牲 AI Album 已证明的大规模效率；关键是规则能机械展开，不能要求 Apply 重新理解语义。

你的回答：B. 我一次性帮你把问题说清楚，就是我们其实之前也讲到了有弱和强两种。假如说XML XML那种格式的话，我们不做一个强制的要求，但其实理论上来说，它的信息应该也是全的。然后在这种不可回溯的前提下，就打个比方，我们如果再结合Precheck Result里面的那个结果，你比如说A有Representative它背后代表了100个，B是个Outlier它就只代表了一个。那这个时候我们虽然只确定A和B，但是因为A绑定的100个这个信息也是在的，所以其实我们是可以还原出这101个完整信息的，这也OK。

整合说明：第 1 轮五题均已回答。Q1 还明确指出：若 Plan 发现代表证据隐藏重要差异，应在 Plan 阶段解决；需要新上游证据时可以退回 PreCheck。Q1 与 Q2 还提出了不可逆操作发生后可能需要 rewind，但未确定这是 Apply 失败恢复还是用户事后反悔功能。以下第 2 轮只追问这些答案直接产生的边界。

### 第 2 轮：压缩决定、安全交接与回退边界

本轮共 6 个问题。它们先确定“紧凑 Plan 怎样仍然完整”和“不可逆操作到底要保什么”，仍不讨论正式字段、Organization Unit、Placement 或 Schema。

#### Q6. Plan 可以直接对 PreCheck 中已有的一组 Source Items 作一个共同决定吗？

为什么问：这是避免百万项重复清单的关键。但“某张代表图代表 100 项”只说明它帮助阅读，不自动说明这 100 项最终应该得到完全相同的组织结果。

#### Q18. Frozen Plan 要保存多少“为什么这样分组”的信息？

#### Q19. 用户怎样确认“就是这一份 Frozen Plan”？

为什么问：用户确认的是压缩展示，但真正冻结的是完整组织结果。系统必须能证明确认后内容没有被偷偷改变，又不需要建立多层复杂 seal 实体。

- B. 用户只确认一个可变 Plan 名称，之后内容可以继续更新。
- C. 每个 Source Item 都单独签名确认。
- D. 不需要保存确认与具体内容的绑定关系。

推荐：A。原因：它只固定一个必要关系——用户确认哪份内容——不预设 version、digest、seal 对象或字段如何实现。
