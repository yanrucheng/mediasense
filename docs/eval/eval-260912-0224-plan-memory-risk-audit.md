这不是一个只要改成“优先相信地图”就能解决的问题。当前及安装版 [Google adapter](../../src/mediasense/geo.py)相同，附近查询使用 `includedTypes: []`、`rankPreference: DISTANCE`，默认最多 10 项。通用附近地点不承诺识别实际到访场所，在密集商场和楼宇环境中尤其可能缺少需要的餐厅。有限候选、有效无结果和查询失败也有不同含义。

消费链还有一个具体缺口。T:447 确实尝试把 `address_candidate` 与 `nearby_place_candidates` 投影给模型，因此不能说它完全没读 Geo；但 T:449 的 19,835-token 输出被截断，可见尾部止于入口索引 36。后续 T:380 的分页只输出路径、成员数、时间范围，T:625 全量汇总只输出 `formatted_address`，没有展开后续的附近餐厅候选。数据在 Tool 返回值或脚本存储中存在，不等于已经进入模型的比较与判断。没有找到对上述香港候选逐项取舍、冲突处理或向用户展示候选的轨迹。

另一个不能忽略的限制是：本次 Result 明确记录 embedding 为 `disabled / no_local_profile_configured`。167 个入口和 2,136 项记账不等于所有潜在餐厅边界都经过内容检验。例如入口 60 单独代表 201 项。本审计没有逐个验证这些成员是否隐藏另一次访问，所以只将其列为压缩限制和需按后果调查的范围，不直接认定分组算法已错。

**B：中途语义确认缺失属实，最终冻结确认被绕过则没有证据。**

T 会话只有三个用户输入：处理数据、授权地理恢复的“行”、以及 T:263 的“直接进入 plan”。进入 Plan 后没有用户对餐厅身份、访问次数或顺序的确认。T:505 的“方向预览”只是说明将按日期和活动整理，没有给出具体用餐节点的候选或邀请用户补齐缺口；T:699 已宣布完整草稿并开始提交。最终没有请求冻结确认，是因为当时工具未能交付可冻结身份。这不能解释或补偿提交前已经缺失的语义互动，也不能被描述为已经越权冻结或 Apply。

Foundation 本来就要求 Agent 询问高影响不确定性、保留确认范围。[Plan Skill](../../src/mediasense/_resources/skills/mediasense-plan/SKILL.md)也已有 conformance checkpoint、directional Preview 和高影响语义确认。问题不是“从未写过交互”，而是这些要求没有在这个结果中成立。

Skill 同时存在一处直接的准则冲突：第 90 行要求 `Ask the Human only when the unresolved branch is a value or retrieval preference they own.`，把提问收窄到价值或检索偏好；第 108 行却允许改变高影响语义边界的问题，第 128 行又承认用户提供地点含义的路径。T:270 保留的实际 Skill 读取输出也包含这一限制，因此不是审计后才出现的文本。用户能够澄清“去了哪家、去了几次、先后如何”，这些不是只能由地图供应商裁定的偏好问题。应当保持的是“用户陈述不能冒充 PreCheck/provider 观测”，并不需要禁止用户补充经历事实。这是有文本证据的责任边界冲突；没有反事实运行，不能断言它是本次模型行为的唯一原因。

Agent 还把“我已经核对”的语气当成了足够可靠的停止条件。虚焦字形被自信读错，说明仅加一个模型自报置信度阈值不能挡住本例。应结合证据质量、相互支持或冲突、候选缺失，以及错误会影响多少素材和什么检索入口来判断是否需要确认。

草稿自测的检索问题是“找牛排刀具”“找厨房合影”等已经出现在自己目录中的标签。它们证明了一部分可浏览性，却没有检验用户真正记得的餐厅名称和访问节奏。把未知餐厅改成泛活动名能避免无依据命名，但不能自动宣称记忆目标已满足。2,136 项各有去向、结构校验通过、与用户记忆对齐，需要各自的证据。

这次当前源码接受包含“晋上馆”的原候选并返回 `seal_ready=true`，恰好说明 [Plan Work 合约](../spec/contract/plan-work/index.md)的边界：它验证覆盖、引用、路径和版本；不识别餐厅，不证明名字真实。不能让一个确定性的结构校验结果替 Agent 和用户承担这项语义责任。

| --- | --- | --- |
| PreCheck 准备来源信息 | PreCheck Result 固定观测、来源和压缩关系；Working Run 管运行；源只读，默认无外部效果 | 位置／视觉材料的实际状态、生产来源、采样损失、代表范围；Result 缺项或失真由其生产者修复，后继 Result 不改写旧结果 |
| Geo 有界获取 | 现有 Geo Tool 管候选、授权、请求记账和恢复；不拥有“到访了哪家”的决定权 | 精确查询点、半径／数量上限、provider、候选和失败；新增网络效果须获得相应授权，不能从已有候选继承无限补查权限 |
| 形成记忆结构、决定何时问 | Plan Agent 按用户目标和授权决定调查、合并、拆分、命名和提问；方法保持开放 | 显示支撑关键节点的证据、真实对立候选和缺口；重要名称、访问边界或先后关系仍不充分且用户可澄清时，请用户确认或明确延后 |
| 补充经历、偏好与接受不确定性 | 用户拥有未委托的语义确认和价值取舍；输入按所说的事件／成员范围进入 Plan | 区分经历陈述、组织偏好、接受残余不确定性和最终版本确认；确认一家店不能扩散成确认整天或全体成员 |
| 保存判断与确认的含义 | 既有 Plan candidate 的 `decision_notes` 配合现有 Source Set 保存实质依据和适用范围；`organization_preferences` 只放真实偏好；Preview 是视图 | 保留“视觉推断／Geo 候选／用户更正／未决”的区别；不把用户店名写成原 Result 观测，不把对话方向接受当作最终身份确认 |
| 持久化与执行安全 | Plan Work Tool 拥有 revision、幂等回执、结构验证和 seal；Apply 仅执行精确 Frozen Plan | 生命周期与请求取消必须真实；最终确认绑定确切 candidate identity；未确认不能 seal，未冻结不能 Apply，Apply 不补做语义决定 |
| 可复用判断知识 | 现有 Plan Skill 指向上述权威并提供充分性、提问和停止准则 | 修正互相冲突的准则；加载 Skill 不证明遵守、不构成授权，也不提供运行状态保证 |

**双锚一放在这里可以落到明确的验收条件。** 目的锚是“用户能凭自己记得的事件、餐厅和节奏找到素材，关键误判不会无声扩散”，归宿锚是“证据留在 Result，解释、用户补充与接受范围留在 Plan，准确版本确认由现有 seal 边界落实”。

确认可以是一次按时间排列的代表图预览、一个简短候选对照，也可以随着发现冲突分批发生。关键条件是：在批量固化关键命名和成员边界前，Agent 已把会改变用户记忆结构的实质缺口带到恰当的决定者，并保存其处理结果。证据充分且用户已委托的部分可直接采用；无法确认的部分可用明确的未知名称或延后处置，但需交代对检索的影响。更强模型若能自行消除这些不确定性，就不需要仪式性地多问一轮。不要固定“第几步必问”、每家店必问、问题数、图像数或统一置信度阈值。

就本例而言，用户已更正的“鲁上鲁”、未定名的旺角晚餐、太子午餐和牛排晚餐，适合作为少量关键节点的复核对象。复核应同时对照各自的时间、代表图、合理候选及成员范围，检查有没有漏掉或混合一次访问；没有可靠候选时可以直接承认缺少店名，不必把无关附近商铺包装成候选菜单。本段是交互样例的选题依据，不是对真实行程或全部成员的新增确认。

后续最小改动应先修正现有 Plan Skill 中对用户事实澄清的排斥，并用相同真实场景验证“候选被实际消费、关键不确定性得到处理、确认范围被准确保存”。针对虚焦高自信误读、附近候选缺少真店、多次访问可能混合，以及用户已明确委托且证据充分的情形分别观察行为；既检验该问时能问，也检验不需要时不会强加问卷。工具发布则按既有[安装与升级 runbook](../../readme/installation.md)完成源码、wheel、日常安装与新会话的逐层验证。当前审计没有替用户批准一份新的合约，也没有把修复安装、业务候选修改或后继 PreCheck 记为已经完成。

**工具审查追加：已确认当前存储边界，是否扩展取决于需要承诺的恢复范围。**

用户随后认可“Plan 对组织决策的信息充分性负责，主动获取信息，目的和归宿稳定、方法开放”的认识，并要求继续核实 Tool 是否需要改变。这一轮沿接收补充信息、形成依据、保存、恢复和最终审阅的路径检查；没有将餐厅或 GPX 升格为通用流程，也没有实施新公共接口。

当前存储边界是：[Plan Work](../../src/mediasense/plan/work.py)的 `update` 要求完整 `candidate_content`，且只在 `analysis.seal_ready` 后调用 store 保存。偏好更新也依附于这次提交。`decision_notes` 属于完整 Candidate，之后进入 Frozen Plan；[Frozen Plan 合约](../spec/contract/frozen-plan/index.md)将其限定为最短有用说明，不容纳完整查询、模型输入或复制的 Evidence。这限制了 MediaSense 自己保存未完成工作的范围，**并不限制 Agent 在调用 Tool 前讨论、调查和使用用户信息**。Agent 可以在会话中先收敛，再把完整组织、真实偏好和最短必要说明一同提交。不能把全部工作信息塞进 decision notes，也不能把事实补充伪装成 organization preferences。

用真实 Plan handler、SQLite store、source-set resolver 和内置 renderer，配合合成的 PreCheck reader 完成了以下调用验证。它验证当前实现边界，不验证真实地图、模型质量、安装版 MCP 传输或一个未来接口。脚本为 `/tmp/mediasense-plan-tool-review/probe.py`；完整调用与精简摘要分别保存在 `/tmp/mediasense-plan-tool-review/run-3ckaaz7y/calls.json`、`summary.json`，摘要包含被测源码 SHA-256。没有写入业务 Dataset，也没有 seal 或 Apply。

| 当前调用／恢复场景 | 实际结果 | 说明 |
| --- | --- | --- |
| Work 创建后只更新用户偏好 | `invalid_request: missing candidate_content` | 用户已经表达的新方向，尚不能独立保存到该 Work |
| 只保存一条有适用范围的补充说明 | `candidate_invalid`，缺 scope、logical_root、groups 等必需内容 | 工作期信息没有独立于完整组织候选的写入口 |
| 组织草稿还缺一个源项去向 | `candidate_invalid: Scoped items have no outcome: source-item:217` | 当前写入接受度与可冻结候选绑定；没有以缺失结果保存探索进展的能力 |
| 完整 Candidate 中保存文字说明，随后新建 Tool 实例读取同一 Store | 成功；说明完整保留，`seal_ready=true` | 现有字段能够保存最终决策的简要说明，不需要另造一个记录所有用户陈述的全局系统 |
| 将 Result 外补充证据填入 `evidence_refs` | `candidate_invalid: reference_not_in_result` | [resolver](../../src/mediasense/source_sets.py)始终通过绑定 Result 的 Read 解析；不能冒造 Result 内引用 |
| 给 decision note 增加补充材料字段 | schema 拒绝 additional property | 当前公开格式没有这项承诺；不能让消费者使用私有扩展冒充已交付能力 |
| 只把一个不存在的文件路径写进说明 | 保存成功，`seal_ready=true` | 文本可保留，不代表材料已留存、身份已绑定或可重新读取；这是结构校验范围的限制，不是路径校验被绕过 |
| 将同一已保存说明交给内置预览器 | `inspect` 有说明，HTML 没有 | [PreviewDocument](../../src/mediasense/plan/preview.py)只持有目录、样本、其他结果与版本绑定，没有 decision notes；若说明承载关键不确定性，使用该 renderer 的界面会漏掉它 |

初始 Work 的默认 `inspect` 还会因默认请求 content 而返回 `candidate_invalid`；显式请求 overview/preferences/validation 可读。这同样体现当前接口面向完整 Candidate 的设计。探索期读取应有清楚的正常返回，但不能把缺 Candidate 包装成一个已成立的候选。

这些多数是当前合约有意设置的范围，并非实现违反原合约。最初审查把“不能通过 Work 保存候选前信息”直接推为“实现主动交互必须扩展 Tool”，中间缺少了一个必要前提：**是否要求 MediaSense 自身恢复尚未提交的探索，而非由 Agent 会话及其已有工作记录承担。** 用户指出这一点后，本报告保留调用事实，修正必改结论。上一轮 Foundation／Skill 草案仍可改善当前接口下的交互；它不应被未批准的存储扩展阻塞。

责任应按可委托的结果来分：Agent 决定如何调查、如何讨论及何时值得保存；Tool 对明确提交的内容提供持久化、读取、校验、版本和授权保证。一个结果若要让后继 Agent 继续，必须保留影响下一步的目的、约束、判断依据、范围和未决事项；这个要求不等于保存全部过程，也不自动要求这些信息只能由一个新 Tool 承载。完整最终成果与尚未完成的工作快照，所需的可继续信息不同。

下列三种方案以“MediaSense 要保存哪个成熟程度的成果”为比较轴，不按材料类型或调查步骤拆分：

| 设计方案 | 它保证什么 | 对 Agent 与业务的收益 | 成本与边界 |
| --- | --- | --- | --- |
| A：仅保存完整候选，沿用当前形态 | 已提交的完整组织可重读、修订、确认和冻结；提交前工作由会话承担 | 调用少、状态简单，Agent 可先完成有意义的讨论；能实现本次希望的主动信息收集 | 不能承诺仅凭 MediaSense 恢复提交前工作；若用户要“先保存这些，明天继续”，需要会话层的可靠记录或另行定义存储能力 |
| B：完整候选为默认，允许可选的工作快照 | Agent 自选时机保存的草稿和必要依据可以继续；保存成功与是否完整分别返回 | 同时支持先讨论后提交、分段工作和跨会话接续；已有 Work 可以拥有这一职责 | 必须定义不完整内容的读取、校验和版本语义，以及何种必要材料确实可恢复；这是一项产品能力扩展，不是原交互的前置条件 |
| C：Tool 管理整个信息收集过程 | 每个输入、问题、候选、处理进度和依赖均由 Tool 跟踪 | 适合明确需要实时协作、审计或自动调度的产品 | 多出实体、状态转换、调用和语义同步责任；当前未证明这些需要，容易限制更强 Agent 的调查方法 |

**如果重新设计 Plan Tool，倾向 B；当前交互修正用 A 就能落地。** B 的目的为保存“值得继续的工作成果”，权威归宿仍是现有 Work；它不复制 Agent 的整个运行过程。是否立即实施 B，应以“先保存部分已知内容，换会话继续”等真实需求和交接例子评审决定，不能用一个人为不合法请求被拒绝作为必要性证明。

若选择 B，最小契约应约束下述结果，而不先承诺新 action 或具体字段：

- Agent 可以直接提交完整成果，也可以在有价值的时机保存一个草稿快照；不要求每轮对话先写 Tool，不规定提问顺序和资料形式。
- 一个 Work revision 说明这次明确保存了什么，包括有用的组织草案、必要约束和决定依据、范围及未决影响。尽量使用同一快照归属，不预设独立的输入版本、候选版本和自动依赖图。编辑只有依据而沿用原组织时，Agent 必须明确此次快照对两者关系的陈述；Tool 不推断新信息的语义影响。
- 保存操作先验证请求有效性、归属、权限和引用规则；允许的“不完整”不包含伪造引用、未授权范围或坏格式。对于已有效保存但尚不完整的内容，返回可定位的缺口，不能返回可冻结身份或将错误路径当成完成。完整提交仍能使用简短路径。
- `inspect` 能重建被保存的工作含义，并区分保存、结构完整、语义接受和最终确认。Tool 只能证明明确提交的信息，不能检测未提交的新对话或保证恢复 Agent 的全部上下文。
- 最终确认绑定实际完整内容和对应审阅；未决事项须在最终处置中解决、明确接受或延后。无关补充不应由 Tool 自动重做语义判断；有意义的组织变化由 Agent 提交新内容，旧确认不能冒用。
- 只有材料本身对继续、质疑或复核仍不可或缺时，才要求稳定读取入口、身份或授权副本。用户陈述的来源和适用范围可能已足够支持简要决策说明；不能把每次补充都升级成独立 Evidence 实体。

内置预览器遗漏已保存的关键说明，是一个独立的呈现限制。如果它承担完整审阅，应让这些信息可见；Agent 用公开 inspect 加自有预览也可以履行这项责任。这个问题本身不证明要扩展 Work 存储或新增预览 Tool。

处理能力的可用性与 Plan Work 存储方案独立。当前 [GPX producer](../../src/mediasense/precheck/gpx.py)需要 `run_id`、`metadata_work_id` 和已采用的相对 Source Item；orchestrator 只从该 Run 已记账的辅助 GPX 构造输入。公开 PreCheck start/resume 没有任意补充材料入口，Geo Tool 的三个 operation 都要求坐标。这证明 MediaSense 当前没有声明好的“Plan 提供一份外部轨迹和有界时间范围，取得匹配候选”公共能力，不能由此推出 Agent 无法通过其他已有、适当且被授权的能力处理资料。需要产品级复用和保证时再扩展适当能力边界；Work 的通用存储本身也不会获得解析能力。其他资料按同一标准审查，不穷举永久文件类型。

Geo 已有请求 journal 和精确幂等重放，提供了可复用的执行证据。缺口不意味着需要另建 Geo 生命周期或复制其私有账本。Plan 如要依赖一次补查，应保留受合约支持的引用／请求上下文或经授权保留的必要结果，不能要求后继 Agent 猜测私有存储。

区分 A 与 B 的评审例子应明确：用户只要求本轮讨论后给出完整成果时，A 已足够；用户希望“先保存当前确定的内容，下次从这里继续”，且接续不依赖原会话时，B 才提供额外的实质保证。用于比较的 B 交接例子可以是一个无完整 Candidate 的 Work，已保存一项用户说明和一个未决关系，后继会话能够定位来源、适用范围和下一步缺口。保存时机和下一步调查仍由 Agent 决定。这是待评审的产品情形，不是本次已由用户要求实施的持久化功能。

两条路径都须保留结果的结构完整性：后继读者不应为了理解所交付成果而重新推导重要遗漏。完整成果需交代重要决定的依据、范围和剩余限制；承诺可继续的草稿还需交代未决事项及其后果。没有固定流程、全量记录或独立信息仓库也可以做到。

验收先检验 A 下主动信息收集、真实采用、确认范围和可理解成果；若选择 B，再加候选前保存与重开恢复、不可用材料、有效但不完整草稿的诊断、并发与版本绑定。还应验证完整成果的一次提交路径没有变成繁琐流程。只有稳定引用或处理能力不足改变实际场景结果时，才扩大对应 Tool 的范围。

兼容政策沿用当前 Plan 合约的 `Not in production / None — Zero BC`，不新增双路由、双写或兼容别名。零 API 兼容不授权覆盖已有 Result／Frozen Plan，也不把工作资料自动混入 Frozen Plan。若实施新的公共承诺，合约、实现、Host、发布副本与实际消费者应一同验证。本轮修正设计判断和评审记录；Foundation／Skill 补丁仍是未应用草案，Tool 方案也尚未实施。
